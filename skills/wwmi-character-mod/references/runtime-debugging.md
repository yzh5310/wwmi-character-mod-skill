# 运行时诊断

| 症状 | 优先检查 | 最小证据 |
|---|---|---|
| 新网格配旧皮纹理 | shader槽位、覆盖优先级 | 同一draw绑定和替换日志 |
| 界面正确、场景错误 | 场景独有通道 | 场景定向采集 |
| 尖角/拉伸 | 源网格、供体、骨骼 | 可比姿势与最终权重差异 |
| 橄榄色表面 | 法线/遮罩当颜色 | 纹理内容和shader读取槽 |
| 衣料像镜像/碎块、看不出结构 | 贴图 V 约定（图像 vs Direct3D） | 原生网格+原生贴图对照渲染 |
| 特定颜色硬边色块（黄绿/品红） | 贴图错绑到颜色槽 | 诊断色替换后色块是否跟随 |
| 远景细纹噪点/斜纹 | 无 mip、过滤或法线噪声 | DDS mip 数、可比远近截图 |
| 底部透视 | 淡出、底面、剔除、裁剪 | 点阵、源网格、远近/角色对照 |
| 双面后黑影 | 阴影/深度也受改动 | 撤回双面，对照上下身 |
| 截图缺右下 | DPI虚拟坐标 | PNG尺寸与物理窗口边界 |
| 刷新没变 | 焦点、真实安装、键是否接收 | 手动刷新与实际编译记录 |

## 材质

按部件选材质，绘制前保存、后恢复槽位。哈希回调在选材质后触发，避免覆盖同atlas的其他使用者。

使用 RabbitFX 等语义 API 前先读实际安装的资源名和分类逻辑。API不保证所有场景变体正确。空哈希覆盖也可能遮蔽描述符过滤；新filter_index也可能覆盖前置分类值。

修槽必须有实际通道证据，不套用统一的normal0/diffuse1表。同一VS在普通与燃烧状态可能配不同PS：基色从t0移到t1，t0改作效果纹理。仅按VS强制换t0可能在高层残留原皮、污染燃烧。阶段相关问题读 [stage-effects.md](stage-effects.md)。

使用额外槽位重定向基色采样时，先核验资源类型、采样器和实际指令指纹；用本Mod逐draw标志门控，并恢复额外槽位与标志。共用shader的原始采样/插件UV初始化应位于局部分支之外，再条件覆盖目标颜色。否则插件可能只在目标分支初始化临时寄存器，影响非目标角色。检查最终组合后的汇编，不只检查自己生成的正则。

鞋底发黑先区分源颜色、错误绑定、法线和光照。按UV采样对应底面，不能用整张图或整个鞋子的平均颜色推断鞋底颜色。判断底面朝向时核对坐标系和存储法线；若三角形叉积在身体和鞋子都与存储法线反向，可能只是统一绕序约定，不应直接翻转鞋底法线。守岸人案例的浅灰鞋底最终随局部修正恢复，但没有单独隔离鞋底因果，不把某一个补丁写成通用鞋底修法。

## 贴图采样方向（V 约定）

离线烘焙常用「图像第 0 行 = V1」的图像空间约定；Direct3D 采样是「第 0 行 = V0」。若把烘焙图集原样写成 DDS，每个 UV 岛都会取到镜像位置的内容，游戏里表现为红黑碎块、迷彩、看不出服装结构。**颜色、法线、AO 图集要一起翻转**（法线的 G 方向在该翻转下保持不变，但要用实物图确认）。

判定方法：拿采集到的**原生网格 + 原生贴图**做对照渲染，分别按两种约定各渲染一次，正确的一组会显示连贯的缝线/包边/结构；再用出问题的 mod 网格和贴图按游戏约定模拟，应能复现游戏画面。可直接用 `scripts/probe_texture_v_convention.py`。实机复核可临时把 diffuse 换成 UV 坐标渐变（R=U、G=V），正确时显示大块连续渐变。

不要靠「离线预览看起来对」来判定，离线渲染器通常和烘焙共用同一套图像约定，会一起错。

## 诊断色定位错绑

怀疑某张贴图被采样到错误槽位时，把该贴图临时替换成高饱和诊断色（例如衬里=品红、内衬=青、皮肤补接=黄），刷新后看画面中的异常色块是否跟着变色：

- 跟随变色 → 是贴图绑定/槽位问题，不是光照或几何。
- 不变色 → 查光照、法线、顶点色或遮罩。

确认是错绑后再定位具体 pass；一次只改一个材质，避免诊断色之间互相混淆。

## 前向通道标记与 G-buffer VS

某些贴图替换逻辑用 `vs == 62101` 之类的 filter_index 判断「前向/基色在 t0」。这个 filter_index 往往来自其他已安装 Mod 的 `ShaderOverride`，**全局生效**，而且可能只覆盖部分组件的顶点着色器变体。

如果某个组件（例如组件4 裙摆/下半身）的 G-buffer VS 没被标记，绘制会走 RabbitFX/材质分支：法线贴图被绑到 t0，而前向着色器在 t0 采样 diffuse，于是出现**黄绿色硬边色块**（法线图典型颜色），且随视角出现/消失。

修复：在生成 Mod 的 INI 里给缺失的 G-buffer VS 补同一 filter_index（确认该 shader hash 没有被其他 Mod 用不同值覆盖）：

```ini
[ShaderOverride<Mod>ForwardVSComponent4]
hash = <该组件G-buffer VS哈希>
filter_index = 62101
```

排查时逐组件核对采集的 TextureUsage/帧日志里的 VS 哈希，不要假设一个组件通过就全部通过。

## 透视与淡出

看到了内部胸衣或头发，不是底部修复证据。先核对角色和完整截图。射线命中源底面只证明源面存在，不证明运行时绘制；法线也不能替代绕序检查。镜头裁剪要用远离身体的对照或相机数据验证。其他角色在可比角度正常是线索，不是唯一原因证明。

先点阵虚化再透视时，检查反虚化开关、shader是否匹配及现有规则是否涵盖当前条件。备份键后暂开 `export_fixed=1`，必要时 `export_shaders=1`，刷新并查真实新增文件；案例中得到 `ShaderCache/*-ps_regex.txt`，不保证所有环境无需重启。优先文本/指定资源，避免重复数GB贴图导出。

ShaderRegex修复要求：

- 定位具体淡出块，不全局删除discard。
- 用真实shader检查正例、负例和非目标指令保留。
- 绘制标志在目标身体才设置；保存旧值并恢复，让其他角色走原路径。正则匹配范围与运行时作用域是两件事。
- 核对临时寄存器、声明去重、规则顺序、槽位冲突；不能照抄案例x240。
- 淡出与材质裁切合并时，说明绕过该条件的副作用；保留表达式不等于保留裁切效果。确认目标身体应为不透明。
- 文件头显示规则应用只证明匹配；还要检查目标/非目标角色、阴影、切人和动作。

### 多层淡出

按真实绘制列表建立部件表：原始 first_index/count、替换 drawindexed、材质、着色器及临时标志作用域。身体恢复而脸或胸前衣料仍虚化时，先查该部件是否被覆盖；不要继续假定全部属于同一个身体draw。

从最终discard向前追踪数据来源。`min(a,b)`取更小的可见度：即使a被设为1，b仍可使表面消失。屏幕遮罩、角色渐隐、阶段效果、纹理alpha可能在同一判定中组合；需要结合完整上下文分辨，不凭常量或变量名命名成“相机因子”。可运行 `scripts/audit_shader.py` 列出线索，再人工追踪。

- 优先修改已确认的不期望遮罩因子，在组合前处理，保留独立纹理alpha和其他discard。
- 不透明身体的最终discard绕过只是有条件的办法；不能扩展到头发卡片、蕾丝或有镂空的衣料。保留原指令文本不等于保留其裁切效果。
- 保存/恢复每个目标draw组的临时参数；扩大作用域前先检查是否嵌套调用，避免一个保存变量被覆盖。各Mod默认使用无冲突参数。共享参数仅在语义完全相同、作用域均恢复的已核验契约下使用。
- 修改正则后查实际导出指令中的门控、寄存器和原表达式，再比较画面。至少看目标部件与更低角度；用户已确认完成时停止索要额外测试，明确哪些是截图验证、哪些是用户确认。

守岸人案例中“只覆盖身体”和“只置一个中间因子为1”都不完整；最终补上脸/头发作用域及另一层屏幕遮罩，细节见 [shorekeeper-case.md](shorekeeper-case.md)。这是定位方法，不是通用正则模板。

## 采集、截图、回退

F8后无新文件先查实际路径、Hunting、快捷键和焦点。用户按键不等于已采集。记录新目录和时间，避免读旧目录；定向dump，收尾只恢复自己改的键。

**自动发送 F10/F8 可能无法被游戏接收。** SendInput 返回事件数只说明 API 调用成功，不证明游戏响应；需要刷新或采集时优先请用户手动按键，并以新增文件/画面变化作为证据。发送后若没有新帧目录或画面无变化，不要反复声称已刷新。

**F10刷新不等于导出。** [3DMigoto上游实现](https://github.com/bo3b/3Dmigoto/blob/master/DirectX11/CommandList.cpp) 的 `FrameAnalysisDumpCommand::run` 在帧分析未激活时直接返回；本案例必须先刷新诊断INI，再用实际 `analyse_frame` 快捷键（当时为F8）激活。不要给未导出的dump消耗“一次性已采集”标志，也不要靠刷新后第N帧保证采到目标。未来版本需核对实现。

轻量参数诊断：全局可暂用 `analyse_options=desc`，在目标材质替换之前插入 `dump = dump_cb buf txt ps-cb2` 等已核实槽位，再触发F8。仅全局desc不保证导出这些缓冲区。核对目标draw及控制draw实际执行、文件时间/尺寸、VS/PS和CB布局；不同pass的cb2可能完全不同。导出少量参数可能没有明显卡顿，不能以“没反应”判采集失败。

本机所用版本 `hunting=0`禁用、`1`直接启用、`2`软禁用且需切换。采集任务要求立即可用时别把2写成已启用；其他版本仍核对实际配置说明。日志优先的轻量采集可暂用 `analyse_options=desc`，该次环境只输出log而未导出缓冲区；确认新目录及文件后再分析。不要把其他版本也只产log当保证。

含中文Mod路径时，日志中的命令名称可能截断。搜不到Mod名或自定义资源名不等于没有绘制；结合原始 `DrawIndexed(IndexCount:..., StartIndexLocation:...)` 和当时生效的VS/PS、资源绑定定位。不能只搜同一行：shader设置可能早于draw并被后续调用继承。

识别「哪个 draw 是 mod 网格」：FrameAnalysis 的 `vb0` dump 文本里带有合并后的顶点数（如 `count=84795`），比搜资源名可靠；原 VB 的 hash 名可能仍是游戏原始哈希，因为 WWMI 只在命令列表内替换缓冲区。

**ShaderRegex/RabbitFX patch 后 PS 哈希会变**（例如 `f8c96a27…` 在 patch 后成为 `36b2debf…`）。用采集时的旧哈希搜不到是正常现象，应按帧日志里实际设置的 PS 哈希和 shader 名定位。抓帧需要先按版本设置 `hunting` 并用实际 `analyse_frame` 键；F10 只刷新配置，不等于抓帧。

配置收尾采用键级比较：记录修改前值及自己写入值，只在当前值仍等于自己写入值时恢复；发现后续变动或来源不明就保留并记录，不能把整份旧配置盖回去。

每次重试前重新读取关键采集键，避免启动器或并行任务把hunting关闭、把采集范围恢复为整帧导出。不要默认上一轮配置仍有效。导出文本仍是旧分支时比较实际指令、时间与安装文件；可换独立规则名帮助辨认，但不能据此断言缓存是原因或新代码已加载。磁盘恢复与运行中已刷新分开记录。

150%缩放可使窗口逻辑尺寸只有物理尺寸的2/3。GetWindowRect前设置线程DPI awareness，在finally恢复；临时收起遮挡窗口后也恢复。存在焦点竞争时仍需查看实际图片，不把Codex窗口截图当游戏QA。

每次截图重新核对当前角色、目标部件是否入画及对照角度。用户可能已切角色；旧截图正确也不证明当前角色正确。只有腿在画面时不能宣布脸/衣服修复；光照和角度变化时明确可比性限制。

失败变量及时回退。cull=none可能影响阴影/深度；整体换绘制通道可能改变光照而没修透视，不作为通用办法。

## 外部复核

按当前会话的Oracle授权与技能说明操作，只提供必要非敏感上下文，先检查dry-run。浏览器没有已确认提交轮次就没有回答；恢复session而非盲目重复，不把CLI默认模型名当实际模型。不可用时如实记录并继续独立本地检查。
